# 复盘

## 状态比调用顺序难处理

项目里最难的不是把搜索、写作和保存接起来，而是失败以后还能说明白发生了什么。

估算工具成功返回，不代表方案可行；脚本第二次生成成功，也不能把第一次失败擦掉。最后显示“完成”之前，还要确认保存用的是当前计划、有效估算和对应的检查结果。这些区别最终落在操作账本、版本和保存事务上，不能只放在提示词里。

## 几个有用的取舍

我把执行入口改成纯聊天，是希望需求、确认和后续修改在同一个地方完成。代价是“开始”不能简单做关键词匹配：否定、引用、条件句、旧版本确认都要处理。输入边界测试比只演示一句“开始执行”更容易发现问题。

对话图和执行图分开也有实际作用。脚本工具运行时仍能接收停止或修改，等工具结束再处理，不需要把整条链取消重做。PostgreSQL任务表足够支撑这个本地项目，也少维护一个Redis服务。

制作规则只保留两种套餐，让预算和重规划容易核查。代价是表达不了任意制作数量和复杂并行排期，这部分没有继续扩展。

## 测试改变了哪些实现

交付阶段曾反复返回空工具调用。草稿和估算都在，但模型仍受到早先写作需求与“先别执行”等历史语境影响。减少交付阶段的无关上下文后，同一个模型就能继续检查和保存。增加重试次数反而不如先整理它实际需要的信息。

MCP连接也出过问题：节点里创建连接，换一个任务关闭，会在保存后触发AnyIO清理异常。把连接交给独立任务持有后，调用和连接生命周期才分开。只测正常返回发现不了这个问题。

还有一个明显的遗漏：预算5时，工具已经算出缺口3，最终答复却只说达到轮数上限。测试因此增加了对最终说明的断言，而不只检查中间估算。前端也发现过失败记录被标成“复用历史结果”，需要区分保留失败和复用成功产物。

## 还想继续做的事

先把长会话的数据拆分和前端包体积处理好，再补Linux环境与负载测试。JSONB聚合适合现在的规模，历史消息和产物继续增长后会变重。

内容质量还需要独立改进。结构完整、来源可点开，不代表文案每句话都准确。后续应增加事实审校，并在有价格和账单资料后核对真实调用费用。
