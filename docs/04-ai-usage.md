# AI 使用说明

项目使用Codex辅助开发。需求、技术选型和关键修改由我主导，AI参与方案讨论、实现、测试和排错。

## 我负责的部分

我确定了React + Vite、FastAPI、PostgreSQL的基础选型，以及Ollama Qwen3和DeepSeek通过YAML切换的接入方式。Agent使用LangGraph双图，工具通过MCP管理；Skill用于产品内Agent，必要脚本注册为固定工具，保存事务留在业务服务。

几个比较具体的修改是：

- 把“点击开始”改为聊天确认。计划先展示，明确回复后才执行；停止和续跑也走聊天，不再加独立控制按钮。
- 明确预算口径。预算只约束最终方案制作成本，工具和模型开销另列；保留两种制作套餐，先把失败恢复和状态一致性做完。
- 调整工作台的信息组织。采用暖色三栏布局，工具卡片始终展开，计划和方案放在右侧，并能查看旧版本、导出文档。
- 把验证重点从正常完成扩展到模糊需求、工具选择、故障注入、成功产物保留和前后端对应。外部服务配置后，又补了DeepSeek、Tavily的实际调用测试和预算、依赖、状态审核。

这些工作包括需求修改、架构取舍和验收要求。外部API凭证及本地环境配置也由我准备。

## AI做了什么

Codex协助把这些要求写成执行计划，草拟和修改前后端代码、迁移、MCP工具与运行脚本；编写并执行自动化测试，分析模型返回、日志和页面截图，再根据失败结果修改实现。文档和案例索引也使用了AI辅助整理。

产品运行时调用的Qwen3、DeepSeek与开发助手用途不同。它们负责识别需求、生成文案、选择工具和决定重规划，调用记录保存在Trace中。

## 怎么验证修改

代码修改以实际运行结果核对：后端170项回归、8组外部业务/网关场景、27项核心审计，以及6项外部场景页面检查和4项功能回归都有保存记录。详情见[测试报告](03-evaluation.md)。

例如，单次脚本故障后，原失败记录保留，新尝试成功；预算10实际估算12时，模型另选规格并复算为8，素材和成功脚本没有重做。[该用例](../examples/external-live/after/audit-auto-failure-replan/evidence.json)同时保留了输入、工具调用、计划版本和最终保存结果。

协议夹具、演示页面和真实API测试分别标注。文案事实仍需审校，未知供应商费用不填0。
